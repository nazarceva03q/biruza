# Бирюза: облачное управление и заявки

Исправление повторов меню: обработанные переходы сохраняются в той же CAS-записи,
что и сессия. Поздний retry старой команды не сбрасывает новый черновик; порядок
входящих сообщений проверяется по conversation_message_id. Успешно отправленные
ответы повторно не отправляются. Проверено регрессионным тестом с VK_912 и загрузкой фото.

Уточнение прав при подключении: bucket policy не заменяет базовый допуск IAM/ACL.
Перед применением разрешающих правил назначить каждому SA минимальную роль НА СООТВЕТСТВУЮЩИЙ БАКЕТ:
callback – storage.uploader на private/media; intake – storage.uploader на private;
catalog – storage.viewer на private; worker – подходящую объектную роль с удалением на private.
Существующая bucket policy затем ограничивает доступ разрешёнными префиксами и действиями.
Не назначать эти роли всему каталогу и не выдавать общий editor/admin.
Для анонимного чтения media дополнительно требуется базовый публичный допуск чтения объектов,
ограниченный политикой только media/*; список и настройки остаются закрытыми.

Состояние: callback бота и read-only каталог подключены в Yandex Cloud; загрузка и сохранение фото через VK проверены владельцем. Intake и worker ещё НЕ подключены, приём заявок не включён. Реальное удаление VK после 30 суток не подтверждено.
Архивы создаются `python scripts/package-cloud.py` в `artifacts/cloud/`.
Не загружайте туда токены, env, события VK или реальные обращения.

## Функции

| Архив | Точка входа, Node.js 22 | Доступ | Назначение |
|---|---|---|---|
| biruza-callback.zip | callback.handler | HTTPS для VK | Проверка группы/секрета/админа, меню владельца |
| biruza-intake.zip | intake.handler | HTTPS для браузера | Проверка и сохранение заявки, без токена VK |
| biruza-catalog.zip | catalog.handler | Только GET | Read-only публичный манифест, без сессий/заявок |
| biruza-worker.zip | worker.handler | IAM, публичный OFF | Доставка, очистка и приватный итог запуска |

Названия предлагаются `biruza-callback`, `biruza-intake`, `biruza-catalog`, `biruza-worker`.
Они НЕ являются подтверждёнными созданными ресурсами. Сначала проверить существующие функции «Бирюзы», чтобы не создать дубликат.
Память 256 МБ; callback/worker timeout 120 секунд, intake/catalog 30 секунд. Функции не требуют npm install.

## Изоляция и права

Два СОБСТВЕННЫХ бакета «Бирюзы»: private и media. Не использовать бакеты/ключи другого магазина.
Private полностью закрыт, без анонимного чтения/list. **Versioning OFF**, иначе старые версии с контактами не удалятся заменой объекта.
В private не включать object lock/backup/репликацию содержимого без отдельного решения о сроках.
Media: анонимный GetObject разрешён только `media/*`; ListBucket, запись и удаление анонимно запрещены.
Все фото проходят MIME, сигнатуру, лимит 10 МБ; URL VK – HTTPS из allowlist, редиректы запрещены.
Файлы сохраняются перед публикацией. Отмена не публикует черновик и не удаляет чужие/совместно используемые файлы.
Неудалённые безопасные фото черновиков допустимы; их уборка отдельно от клиентских заявок.

Разделить сервисные аккаунты/ключи по функциям. Минимальные object permissions:

| Функция | Private | Media |
|---|---|---|
| callback | read/write catalog/, sessions/, events/, routing/ | write media/ |
| intake | read catalog/; read/write requests/, limits/ | нет |
| catalog | read catalog/ | нет |
| worker | list requests/; read/write/delete requests/; read/write worker/ | нет |

Статические ключи – только в окружении/Lockbox, не в сайте. `.env.example` содержит имена, не значения.
Таймеру отдельный SA с functions.functionInvoker, без storage/editor/admin и без статического ключа.
Предпочтительно ограничить invoker самой функцией; если консоль требует scope каталога, записать фактическое ограничение.
У bucket lifecycle отдельные правила: `limits/` 2 суток, `events/` 2 суток, `sessions/` 2 суток.
Это отдельная техническая политика, worker заявок эти префиксы не удаляет. Контактов покупателя в них нет.
На `requests/` lifecycle НЕ ставить: оно не заменяет процесс удаления VK и технических квитанций.

## Окружение

Для каждой функции: YC_S3_ACCESS_KEY, YC_S3_SECRET_KEY её собственного SA; BIRUZA_PRIVATE_BUCKET.
Callback дополнительно: BIRUZA_MEDIA_BUCKET, BIRUZA_MEDIA_BASE (`https://storage.yandexcloud.net/ИМЯ`), VK_GROUP_ID, VK_GROUP_TOKEN, VK_ADMIN_IDS (через запятую), VK_CALLBACK_SECRET, VK_CONFIRMATION_TOKEN.
Intake: REQUEST_HMAC_SECRET (случайный, минимум 32 символа), CONSENT_VERSION (только утверждённая редакция), VK_REQUESTS_CHAT_ID, ALLOWED_ORIGINS (точные HTTPS origins через запятую), INTAKE_ENABLED=false до сквозного теста.
Worker: VK_GROUP_TOKEN, VK_REQUESTS_CHAT_ID, REQUEST_HMAC_SECRET, CONSENT_VERSION, CLEANUP_APPLY=false, DELIVERY_ENABLED=false.
Catalog больше секретов не требует.
Discovery и диагностическое удаление по умолчанию false: VK_DISCOVERY_ENABLED, VK_DELETE_TEST_ENABLED.
Не менять REQUEST_HMAC_SECRET до окончания хранения существующих заявок: это ключ отпечатков и rate limit, не публичный фронтенд-ключ.

## Меню владельца

В личных сообщениях сообщества команда «Начать». Доступ только VK_ADMIN_IDS.
Добавить → категория → фото/«Готово» → название → состав → описание → цена → хит → предпросмотр → сохранить.
Изменить/удалить → поиск названия → карточка → редактирование поля/подтверждение удаления.
Отмена возвращает в меню без публикации. Устаревшие кнопки отклоняются.
При конфликте изменения другим администратором карточка не перезаписывается: заново откройте её.
«Фотографии оформления» → одна из трёх галерей → фото → «Готово» → предпросмотр → сохранить.
В исходном порядке остаются 3/2/6 фото, новые идут после них. CAS защищает одновременные добавления; операция VK идемпотентна.
Функций административных остатков, продления срока заявки, PHP-панели или REG-релея нет.
Количество в покупательской корзине сохраняется.

## Все входы форм

Общие поля: имя, телефон, способ связи, желаемая дата, пожелания, отдельное согласие/версия, honeypot.
Заголовок не определяет доверенный тип. data-request-type передаётся явно, сервер использует фиксированное перечисление.

| Кнопка/раздел | requestType | Дополнительно | Заголовок VK |
|---|---|---|---|
| Корзина → Оформить с флористом | cart | id/quantity, получение, время, адрес, открытка | Заказ из корзины |
| Квиз → Получить варианты | gift | ответы квиза в пожеланиях | Подбор подарка |
| Сертификаты | certificate | номинал можно указать в пожеланиях | Сертификат |
| Свадебные композиции | wedding | дата/пожелания | Свадебные композиции |
| Открытия магазинов | store_opening | дата/пожелания | Открытие магазина |
| Праздники и мероприятия | event | дата/пожелания | Праздник или мероприятие |
| Индивидуальный букет | custom_bouquet | пожелания/бюджет | Индивидуальный букет |
| Карточки особенных дат | holiday | название праздника, пожелания | Подарок к празднику |
| Задать свой вопрос | question | текст вопроса | Вопрос магазину |
| Надувание ваших шаров | balloon_inflation | пожелания/количество в тексте | Надувание шаров клиента |
| Связаться с флористом | consultation | Прямые call/messenger ссылки, формы нет | Зарезервированный тип Консультация |

Все сообщения идут в одну собственную закрытую беседу, но с разными заголовками.
Цена из браузера не принимается; названия товаров берутся из серверного каталога. Стоимость всегда согласует флорист.
API: POST application/json, Idempotency-Key=`13-digit-timestamp.UUID`; max 20 КБ.
`{accepted:true,id,delivery}` означает сохранение. Доставку выполняет worker; неизвестный исход не называется доставленным.
Rate limit: CAS-счётчики по HMAC IP (20/час) и общий (200/час), полные IP не сохраняются.
Проверяется платформенный sourceIp; CORS/honeypot не считаются достаточной защитой сами по себе.

## Сроки и восстановление

Первое содержимое и routing intent создаются одним условным PUT до обращения к VK.
receivedAt/expiresAt неизменяемы: ровно 30×24 часа. Повтор ключа с другим нормализованным содержимым → 409.
Неизвестный ответ клиент повторяет с тем же ключом; форма/корзина не очищаются.
Delivery: CAS lease; до вызова сохранены peer и стабильный random_id каждой части; все cmid записываются отдельно по частям.
Не более 3 отправок за 5 минут с начала первой попытки. После окна/лимита – review, без бесконечного retry.
Это не гарантия exactly-once внешнего VK. Потеря ответа и ограниченная дедупликация API учитываются как неопределённость.

По сроку CAS заменяет запись на техническую квитанцию без payload. При сбое нет разрыва «payload удалён, receipt не записан».
Старый конкурентный writer не может вернуть payload, потому что все записи перечитывают текущую версию с ETag.
Через 2 минуты после срока разрешается внешняя очистка (время завершить in-flight VK-вызов).
Точное подтверждение messages.delete: peer_id+conversation_message_id, response===1, без error, для каждой части.
Статусы: cloud_purged, vk_pending, vk_api_confirmed, review. API-подтверждение не заменяет проверку у второго участника.
Сбой VK не мешает облачной очистке. До 5 попыток удаления с паузой 24 часа; без текста/контактов.
Технические квитанции/tombstone хранятся до 37 суток от первого приёма (7 суток после payload), затем удаляются.
Ключ без записи принимается только в первые 24 часа с момента создания, поэтому старый ключ не воскрешает удалённую заявку.
Worker листает порциями, хранит курсор последнего обработанного ключа. Итог в private `worker/last-result.json`, без payload/ID клиентов.
При остановке таймера очищение не происходит; требуется наблюдение за итогом и восстановление расписания.
Срок удаления из VK через 30 дней **НЕ ПОДТВЕРЖДЁН**. Не обещать его покупателям до живого возрастного теста.
Автоматические сообщения владельцу об ошибках не включены; отдельного согласования нет.

## Порядок подключения (выдавать пользователю по одному шагу)

1. Проверить существующие ресурсы «Бирюзы», сообщения/бота сообщества, временный адрес статического сайта и облачный каталог.
2. Создать/выбрать собственные бакеты с указанными правами; проверить anonymous 403 private и versioning OFF.
3. Установить callback; секрет/confirmation – из настроек именно этого сообщества. Включить message_new/message_event. Проверить меню владельца.
4. Владелец создаёт закрытую беседу, добавляет сообщество администратором. Discovery временно true, точная команда «Проверка подключения заявок»; peer берётся из аутентифицированного события. Записать peer в окружение, discovery false.
5. Установить intake/catalog/worker, INTAKE_ENABLED=false, CLEANUP_APPLY=false, DELIVERY_ENABLED=false. Убедиться worker непубличен.
6. Синтетический режим локального клиента/консоли: собственный endpoint, утверждённая тестовая версия согласия, точный тестовый origin; только вымышленные контакты. Временно разрешить intake и delivery на своих ресурсах.
7. По каждой реальной форме проверить сохранение, повтор, все поля, receipt cmid и отсутствие дублей. Ошибку/таймаут проверить отдельно, не по настоящим контактам.
8. Свежий diagnostic delete: VK_DELETE_TEST_ENABLED=true, ответить «Проверить удаление» на собственное discovery-сообщение. Проверить у второго участника; флаг false. Сохранить отдельное помеченное сообщение для реальной проверки возраста >30 суток, не подменять дату объекта.
9. Таймер worker: отдельный invoker, функция/тег явные, `* * ? * * *` (каждую минуту, UTC), payload пустой. Сначала preview; DELIVERY_ENABLED можно включать отдельно, CLEANUP_APPLY=false. Проверить срабатывание и приватный last-result.
10. Включить CLEANUP_APPLY=true после тестов облачного удаления. Включить публичный клиент только после согласия/реквизитов и всех сквозных тестов. Пока старое VK-удаление не проверено, отразить ограничение в политике.

Остановить: отключить таймер в Cloud Functions → Триггеры; INTAKE_ENABLED=false останавливает новые заявки.
CLEANUP_APPLY=false останавливает удаление; DELIVERY_ENABLED=false – отправку. Отдельно останавливать callback не требуется.
Реальные имена ресурсов/URL и результаты smoke test фиксировать в игнорируемом artifacts/, без секретов.

# Удаление фото оформления

Кнопка «Удалить товар» принимает название товара или раздела оформления. Для раздела выберите результат поиска, перелистайте фотографии и подтвердите удаление выбранного снимка. Поиск учитывает похожие слова, распространённые окончания и небольшие опечатки. Удаляется запись из выбранной галереи; сам файл не удаляется, чтобы сохранить другие ссылки на него. Повторы события безопасны, параллельное добавление фото не теряется.

Поиск товаров для изменения/удаления и выбор фото оформления используют native VK carousel (`messages.send.template`). До 10 вариантов в одном сообщении; следующие страницы обновляют это же сообщение через `messages.edit`. Выбор привязан к ID и текущей ревизии сессии. Листание внутри страницы выполняет клиент VK (стрелки/свайп при поддержке клиента), без новых сообщений бота. Исходные фото сайта и медиа облака загружаются в VK перед отправкой карусели; ошибка загрузки не подменяется каруселью без снимков. Проверка реального отображения выполняется после загрузки callback-архива.
